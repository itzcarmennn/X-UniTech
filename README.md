## 2.5 Failure Point Consideration

We identified potential failures involving data cables, sensor interference, camera lighting, and steering components, with preventive measures implemented to improve system reliability.

**(i) Data Cable:** Loose cables caused by robot movement and vibration may interrupt sensor connections. We check all connections before each run and ensure cables are properly secured.

**(ii) Gyro Sensor:** Magnetic interference may cause inaccurate heading readings and turning angles. We use an improved mounting position above the Steering Motor and verify readings before each run.

**(iii) Pixy Camera:** Lighting changes may affect pillar recognition and distance estimation. We angle the camera downward to reduce interference from overhead lighting.

**(iv) Steering Mechanism:** Repeated steering movements may cause axles to slide, resulting in loose linkages or inaccurate steering. We secure axles with bushes or stoppers and inspect connections regularly.

# 3.0 Software Architecture and Obstacle Strategy

## 3.1 Open Challenge State Machine with Rationale

•  State A determines the navigation <strong><ins>direction</ins></strong> based on surrounding wall distances.  
•  State B repeats the navigation <strong><ins>sequence</ins></strong> through a loop to reduce code duplication.  
•  State C uses coordinate feedback to fine-tune the robot's <strong><ins>final position</ins></strong>, ensuring a more accurate stopping point.

## 3.2 Obstacle Challenge State Machine with Rationale 

•  State A handles the initial navigation and uses Ultrasonic to guide the robot <strong><ins>out of the parking area</ins></strong>.  
•  State B manages <strong><ins>obstacle navigation</ins></strong> by combining sensor data to detect walls, recognise pillars and avoid obstacles.

**Conclusion:** The optimal Pixy camera parameters were selected based on experimental accuracy, with **greenFollow = 140, redFollow = 120, gAvoid = 130, rAvoid = 110, greenAvoid = 245 and redAvoid = 10**, to improve pillar tracking precision, ensure timely avoidance and minimise collision risks during autonomous navigation.

# 4.0 Systems Thinking and Engineering Decision

## 4.1 Subsystem Interaction

<p align="center">
<img width="600" alt="Screenshot 2026-11-15 162623" src="https://github.com/user-attachments/assets/3ef2762a-71f9-45f1-b4ec-f846b5a379a9" />
</p> 

• The **five subsystems** work together to achieve autonomous navigation.  
• The Vision and Obstacle Detection Systems identify pillars, walls, and surrounding distances, while the Gyro and Colour Sensors help track the robot's heading and position on the field.  
• The Navigation System processes this information to decide the next movement, and the Control System sends commands to the motors.   
• Meanwhile, the Mechanical System allows the robot to move and turn as required.

## 4.2 Explicit Constraints

<p align="center">
<img width="700" alt="image" src="https://github.com/user-attachments/assets/6cdfecaf-d0b4-463e-9a87-240c11f91a75" />
</p> 

**(i) Physical Constraints:** We designed the robot to stay within the 300 mm size limit while keeping the camera high and the robot lightweight at 800 g.  

**(ii) Platform Hardware Constraints:** Since the EV3 Brick has only four sensor ports, we used a MUX to connect both Ultrasonic Sensors through one port.  

**(iii) Component Constraints:** The EV3 Brick, motors, and sensors take up a lot of space, so we designed a custom 3D-printed chassis to fit all components neatly.

**(iv) Computational Constraints:** Due to the EV3's limited processing power (300MHz), we used simple calculations, predefined values, and structured program logic to keep the robot running efficiently. 

## 4.3 Trade-off Constraints

**（i）Physical Constraint – Camera Height**

<p align="center">

• We tested different camera heights and found that 295 mm provided the best detection performance, successfully detecting and avoiding all pillars in 3 out of 3 trials.  
• Therefore, we selected **295 mm** to maximize the camera's viewing range while maintaining a controlled driving speed.

**(ii) Platform Hardware Constraint – Sensor Coverage**

<p align="center">

• We selected **two Ultrasonic Sensors** instead of one to monitor both sides of the robot.  
• Although this required an additional MUX and more wiring, testing showed an improvement in navigation success from 20% to 100%.

**(iii) Component Constraint – Educational Accessibility**

<p align="center">

• A custom **3D-printed chassis** was developed to overcome its space limitations.

**(iv) Computational Constraint – Programming Performance**

 ## 4.4 Iteration Cycles

**Justification:** Established a basic robot design to test fundamental movement and navigation, providing a starting point for identifying design limitations.

<strong><ins>Generation 2: Mechanical Improvements</ins></strong>  
**Justification:** Introduced two Medium Motors, smaller wheels, and dual Ultrasonic Sensors to improve manoeuvrability and obstacle detection.

<strong><ins>Generation 3: Further Optimisation</ins></strong>  
**Justification:** Removed steering gear reduction to achieve faster steering response and focused on improving navigation algorithms and software performance.

<strong><ins>Generation 4: Final Generation</ins></strong>  
**Justification:** Introduced a custom 3D-printed chassis with dedicated component mounts to simplify assembly, improve accessibility, and support easier maintenance.

# Github Content Justification

**models:** This folder contains the 3D CAD models of all four robot generations, including chassis designs, mechanical structures and custom 3D-printed components. The files are provided in `.LXFML` and `.io` formats.  

**others:** This folder contains supporting documents, including the fourth-generation robot building instructions and the Robot Development & Iteration Cycle.  

**schemes:** This folder contains electrical schematics and wiring diagrams of the robot's electronic components, sensors and motors, including the configurations for both the Open Challenge and Obstacle Challenge. The files are provided in PDF format.  

**src:** This folder contains the source code, programming flowcharts and state machine diagrams for all four robot generations, covering both the Open Challenge and Obstacle Challenge.  

**t-photos:** This folder contains photos of the X-UniTech team participating in the WRO 2026 Future Engineers Category.  

**v-photos:** This folder contains photos of all four robot generations from different perspectives, including the front, rear, left, right, top and bottom views.
